# Homebrew Adventure & Card Builder Plan

## Goal

Make The Living Table useful beyond first-party adventures by letting a Dungeon Master assemble adventures from existing cards and create new cards without leaving the product or learning its internal data model.

The homebrew workflow must feel like a guided tabletop authoring tool, not a developer form.

## Primary DM workflow

### Adventure Builder

1. Create Adventure
2. Choose rules edition support: 2014, 2024, or dual-edition
3. Add adventure metadata: title, level range, party size, expected duration, synopsis, content tags
4. Build Scenes in order
5. Drag reusable cards from the Library into each Scene
6. Assign each card to its default live-board slot
7. Add conditional/optional cards and encounter scaling rules
8. Add read-aloud text, DM notes, clues, triggers, exits, and failure-forward outcomes
9. Preview the Scene exactly as it will appear on the DM board
10. Run validation
11. Save as draft / duplicate / export / play

## Existing-card library

The Library should expose cards as reusable game objects with filters for:

- card type
- 2014 / 2024 / dual / homebrew
- character level or monster CR
- environment
- damage type
- creature type
- rarity
- source/adventure
- tags
- official/SRD-compatible vs homebrew
- owned / created-by-me / favorites

Primary actions:

- Add to Scene
- Preview front/back
- Clone as homebrew
- Add to favorites
- Inspect rules provenance

## Scene Composer

The composer should visually mirror the live seven-slot board:

- Location
- Site
- Area
- NPCs
- Monsters
- Traps/Hazards
- Treasure/Rewards

A DM drags cards directly into those slots. The composer stores placement data, not visual coordinates, so it remains responsive and compatible with the live board.

Each Scene additionally stores:

- Scene title
- read-aloud text
- DM notes
- objectives
- entry conditions
- exits / next Scenes
- optional branches
- clues
- encounter scaling
- reveal state defaults
- card quantities
- reinforcements / triggered cards
- success/failure transitions

## Live preview

The builder must show the actual canonical card while editing.

Desktop layout:

- left: guided fields
- center: live card front/back preview
- right: validation, rules warnings, tags, board placement

On smaller screens the same sections stack.

The preview is generated by the same card renderer used in play. There must not be a separate homebrew-only visual renderer that can drift from first-party cards.

## Theme controls

The product owns:

- card dimensions
- typography
- icon vocabulary
- stat-band layout
- front/back hierarchy
- accessibility contrast
- print-safe margins
- responsive behavior

The user controls:

- artwork
- title
- subtitle/type labels where appropriate
- content
- approved accent/theme token
- tags

No arbitrary CSS or unrestricted font/color controls in the normal builder.

## Rules assistance

The builder should calculate common values when enough inputs exist.

Examples:

- ability modifier from ability score
- proficiency bonus from level/CR where the selected rule model defines it
- attack bonus from proficiency + ability + magic bonus
- damage modifier independently from attack proficiency
- spell save DC and spell attack from caster profile
- AC from selected armor/equipment for character cards
- passive scores from ability/skill state

The user can override calculated values only by explicitly marking the mechanic as homebrew. Overrides should show a visible Homebrew badge and preserve the original calculated/reference value for comparison.

## Validation levels

### Rules-valid

Passes strict validation for the chosen supported rules profile.

### Homebrew-valid

Mechanically usable but intentionally differs from baseline rules. Warnings may be present, but the card can be saved and played.

### Incomplete

Cannot be reliably used by the runtime. Examples: a save action with no DC, damage button with no dice, spell attack with no attack formula, missing board type.

Incomplete cards can be saved as drafts but should not be publishable/playable without an explicit safe fallback that disables unavailable automation.

## Combat shortcut generation

Combat shortcuts are derived from structured mechanics; authors never type the button math separately.

Examples:

- INIT derives from initiative data
- Attack derives from structured attack object
- Damage derives from that attack's damage expression
- Save derives from save ability + DC
- Recharge derives from recharge rule

If structured data is incomplete, no automated shortcut is shown.

## Adventure validation

Before an adventure can be marked Playtest Ready, validate:

- every referenced card exists
- all Scenes are reachable or intentionally optional
- no dead-end essential path without a declared ending
- required clues are not accidentally single-point failures unless intentional
- every Scene placement maps to a valid board slot
- monster quantities and scaling rules are valid
- player-visible cards do not expose DM secrets
- all required rule-bearing cards are Rules-valid or explicitly Homebrew-valid
- artwork/alt text requirements are met
- adventure start and ending are defined

## Storage model

Long-term homebrew objects should have stable IDs and revisions.

Suggested hierarchy:

- User Library
  - Cards
  - Characters
  - Adventures
- Adventure
  - metadata
  - ordered Scene graph
  - card references + quantity + placement + overrides
- Card Definition
  - base content
  - rules profile
  - artwork metadata
  - provenance
  - revision
- Runtime Card Instance
  - definition ID + revision
  - current state (HP, charges, reveal, ownership, conditions, etc.)

Adventure definitions must reference card definitions rather than copy-pasting entire card bodies whenever possible. Cloning creates a new definition with provenance pointing to the source.

## UX principles

- Drag-and-drop first, but every action must also work by keyboard/button controls.
- Progressive disclosure: show basic fields first; advanced mechanics only when requested.
- Never require a DM to understand JSON, CSS, repository files, or schemas.
- Preview continuously; avoid a separate 'compile' mental model.
- Explain rule warnings in plain language and show the formula that produced calculated values.
- Preserve drafts automatically.
- Provide Undo/Redo for authoring actions.
- Make cloning an existing card the fastest path to homebrew.

## Delivery ladder

### Phase 1 — Library + Adventure Composer
- browse/search reusable cards
- create an adventure
- create/reorder Scenes
- drag cards into seven board slots
- save/load draft locally
- play a locally authored adventure

### Phase 2 — Card Builder
- clone cards
- guided templates for Monster, NPC, Item, Trap/Hazard, Location/Site/Area
- canonical live preview
- structured combat shortcuts
- validation states

### Phase 3 — Spell + Character Builder
- spell builder with compact spell-card generation
- character/pregen builder
- edition-aware calculations
- equipment/backpack setup
- spell deck generation

### Phase 4 — Publishing & Sharing
- account-backed libraries
- versioned adventures/cards
- import/export packages
- share/private/public controls
- attribution/provenance
- marketplace/community features only after licensing, moderation, and security requirements are complete

## Definition of Done for the first Homebrew MVP

A DM can start from the Home page, create an adventure, add/reorder Scenes, search existing cards, drag them into correct board slots, clone or create a card with the canonical template, save the adventure, launch it on the DM Table, advance Scenes, and have the Player Table receive the correct player-safe cards — without editing source code.
